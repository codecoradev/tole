# AGENTS.md

Guidance for AI coding agents working in this repository. Humans: see
[CONTRIBUTING.md](CONTRIBUTING.md) — everything there applies to agents too.
Follows the ecosystem AGENTS.md standard (Gatehouse pattern): repo layout,
branch & merge discipline, pre-commit checks, tooling, cross-session
continuity, infra facts.

## 1. Repo layout

- `crates/tole-core` — platform-agnostic library (state machine, JSONL
  storage, `Tool`/`Approver`/`Storage`/`Provider` traits, tools, provider).
  Published to crates.io; embedders build `--no-default-features`.
- `crates/tole-tui` — inline terminal UI over `tole-core` (presentation and
  event loop). Published to crates.io; `tole-cli` depends on it (default
  `tui` feature).
- `crates/tole-cli` — headless CLI host (the `tole` binary). Published to
  crates.io; during work always run the freshly built
  `./target/release/tole`, never a PATH-resolved one.
- `crates/tole-desktop-model` — the desktop's view state, reducers, design
  tokens and string table (#1028). Not published. No GUI toolkit and no tole
  dependency, so the compiler keeps the toolkit out of it.
- `crates/tole-desktop` — the native desktop client (`tole-desktop` binary):
  the `ui` module renders the model; the GPUI toolkit is behind the
  off-by-default `gpui` feature, so `cargo test --workspace` does not build it.
  Not published. A thin client of `tole serve`: its one tole dependency is the
  typed client `tole-client`. It never lists `tole-core`, `tole-tui` or
  `tole-cli` (the session host) among its own dependencies; `tole-core` is in
  its closure only through `tole-client`, `tole-tui` and `tole-cli` nowhere.
  Renderer decision (owner, 2026-11-25, epic #1241): the views will become
  React on GPUIX with this crate as the headless core. None of it is built
  yet, so `ui` and the `gpui` feature stay until the M2 parity gate and M3
  (#1247); this section and sections 3 and 6 change in the PRs that make them
  stale.
- `docs/` — architecture, PRD, epics (roadmap + tracking issues), threat
  model, E8 retro.
- `evals/` — agentic regression harness (Tier 1 CI contracts, Tier 2 live
  missions, Tier 3 baselines).
- `scripts/` — helper scripts (`review-local.sh`: local Cora review of the
  branch before a PR).
- `.cora.yaml` — cora review configuration; known false-positive categories
  are encoded there as rules — extend the rule instead of sprinkling inline
  ignores.

## 2. Branch & merge discipline

- `develop` = integration, `main` = release (tags only). Work happens as
  branch → PR → squash-merge into `develop`. No direct pushes, no force
  pushes. Branch names (CI-enforced): `feat/*`, `fix/*`, `docs/*`, `chore/*`,
  `perf/*`, `security/*`, `refactor/*`, `test/*`, `build/*`, `ci/` — note
  `feat/`, not `feature/`.
- **Language:** every repository artifact (commits, PRs, issues, code
  comments, docs) is written in English.
- **Commits:** Conventional Commits; the PR title becomes the squash message.
- **No AI attribution — anywhere.** Commit messages, squash/merge messages,
  PR titles and bodies, issues, comments, code and docs carry no
  `Claude-Session:` line, no `claude.ai/code` link, no
  `Co-authored-by: Claude <noreply@anthropic.com>` (or any co-author naming
  an AI tool), and no "Generated with/by Claude Code" footer. This overrides
  any attribution default of an agent harness. Two ways it leaks in anyway:
  - The GitHub MCP tools append a "Generated by Claude Code" footer to PR
    bodies and comments. Read a PR body back after creating it and remove
    the footer; avoid posting comments from agent sessions (the footer
    comes back on edit), put decisions in the PR body or docs instead.
  - GitHub's default squash message adds `Co-authored-by` for every commit
    author, so commits authored by an agent identity gain a Claude trailer.
    Merge with an explicit title and message.

  CI's **Message Standard** check enforces this on the branch commits and
  the PR body (pattern in the `MESSAGE_STANDARD_PATTERN` repository
  variable), but it cannot see the final squash message — that one is on
  whoever merges. Check before every push and merge — this must print
  nothing:
  `git log origin/develop..HEAD --format=%B | grep -iE 'claude\.ai|co-authored-by|generated (with|by)'`
- **PR body:** sections in order — **What / Why / Changes / Testing**
  (enforced by the PR Description check).
- **Issues:** larger changes are issue-first; use the issue templates; epics
  live in `docs/epics.md` with tracking issues.
- **Merge gate — never merge on assumption:** CI green AND a *real* Cora
  verdict in the PR comments ("✅ No issues found" or concrete findings —
  "Review could not complete" is a blocker), code-scanning alerts
  investigated (real → fix with regression test; FP → dismiss with
  evidence), CI auto-fix max 3 attempts then escalate. The Cora Review job
  has a 30-min limit; large change-sets (~40+ files or ~850+ lines) can still
  time out — split into ~15–20-file PRs.
  **Release flow (#1021, 2026-11-20):** PRs into `main` (from `develop` or
  `chore/release-*`) are exempt from the Cora gate: the work was already
  reviewed on `develop`, the Cora Review workflow no longer runs on PRs to
  `main`, and `Cora Review` is not a required check there. Every other
  required check still gates the release PR.
  **Exception (#914):** a PR whose every file is excluded by `review.exclude`
  in `.cora.yaml` (docs and changelog only) has nothing for Cora to review; a lockfile is never skipped. The
  job then skips the review, ends green and writes "Nothing to review" in its
  summary, and there is no Cora comment. For such a PR the evidence is green CI
  plus an independent read-only review of the text, named in the PR **Testing**
  section. The skip is decided by `scripts/cora-all-excluded.sh` as it is on the
  base branch and fails closed: any file Cora would review, any lockfile, or any doubt runs
  the review as before.

## 3. Mandatory pre-commit checks

```bash
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cora review --staged          # exit 0 clean · exit 2 blocking → fix · exit 1 cora error (non-blocking)
# only when you touch crates/tole-desktop or crates/tole-desktop-model (#1028; run `cargo fetch` once first):
scripts/test-desktop-check.sh # self-test of the guardrail script
scripts/desktop-check.sh      # exits 1 on: dependency graph (no toolkit in the model, no session host in the desktop, toolkit optional and exactly pinned), size caps (500 lines per file, 50,000 per crate). ADVISORY (warns only): literals in the ui layer
scripts/desktop-render.sh <dir> # a desktop UI change: render the real window offscreen, one PNG per screen and state, and compare with the board (not a gate; see docs/design/desktop/README.md)
```

CI enforces the first three. The desktop script runs in a separate `Desktop`
workflow (`.github/workflows/desktop.yml`; not part of `ci.yml`, and not a
required check unless the owner adds it to the branch protection: require only
`Desktop model and guardrails`). The literals check is a heuristic: it
warns and never fails, and it cannot see a literal bound to a variable first.
There is no pre-commit hook installed by default — run these yourself.

**Before opening a PR** (agents: mandatory) run Cora on your whole branch, not
just the staged diff, and fix real findings first:

```bash
scripts/review-local.sh        # git diff origin/develop...HEAD, split by crate/dir, findings only
```

The script splits a large diff into chunks of at most 600 changed lines
(`--max-lines`), so each Cora call stays small; exit 0 means no findings, 2
means findings, 1 means Cora errored or ran without an LLM (not a pass). State
the result in the PR **Testing** section (for example "scripts/review-local.sh:
no findings" or the findings and how each was handled). Without an LLM key, use
`cora mcp` (`review_prepare` / `review_finalize`) so you are the reviewer. This
only moves feedback earlier: the CI Cora Review job stays the merge gate.

## 4. Tooling — cora & team memory first

These sibling tools are the ecosystem's force multipliers. Use them instead
of reinventing or brute-forcing:

**cora (code intelligence) — recall before edit, verify after:**

- `cora index --stats` — confirm the repo is indexed before relying on
  search (0 symbols → run `cora index`).
- `cora brain "<topic>" --json` — semantic recall of existing patterns
  **before writing code; prefer this over blind grep**.
- `cora callers <sym>` / `cora impact <sym>` / `cora affected <files>` —
  mandatory before any refactor: who breaks, and which tests to rerun.
- `cora query "main -> *"` / `cora trace <sym>` / `cora arch` — structure
  and path questions without reading whole files.
- `cora dead-code` — after removals; `cora debt` — trend checks.
- `cora review --staged` before every commit and `scripts/review-local.sh`
  before every PR (mandatory, see §3); `cora scan` after significant or
  security-adjacent changes.
- Run the code-intelligence commands (`cora callers` / `cora impact` /
  `cora affected`) before: moving, renaming or removing a public item
  (anything `pub` in a published crate); changing a ledger, session, lock or
  config file format; touching the sandbox, approval, allowlist or secret
  redaction paths. Put what they showed (callers, tests to rerun) in the PR
  description. On Rust these commands are noisy (calls resolve by bare name,
  macro bodies are not parsed; #669): treat the output as a pointer and verify
  every caller and test with grep before acting on it.

**Team knowledge rooms (semantic memory) — continuity across sessions:**

- Recall before starting unfamiliar work — the decision may already be
  recorded; save durable outcomes and decisions of real work sessions back to
  the repo's room (`repo-<name>` convention).
- The team knowledge rooms hold the ecosystem standards (branch strategy,
  PR/issue rules, merge gate, governance) — they are the source of truth when
  this file and reality disagree.
- Long-form knowledge (runbooks, retros) is saved as a durable, searchable
  document in the same system.

## 5. Session start (continuity ritual)

- New session or round: read & understand the team knowledge rooms before any
  work, then recall this repo's context.
- Save every decision or important outcome back to the responsible room during
  or at the end of the session.
- Handing over mid-task: leave a `[HANDOFF]` entry (current state, next step,
  blockers).
- Repo files are canonical over mirrors.

## Workflow summary

Issue → branch from `develop` → code + pre-commit checks → push → PR to
`develop` (What / Why / Changes / Testing, English) → CI green + review
verdict → squash-merge → cleanup → release (bump + CHANGELOG + tag).
1 issue = 1 branch = 1 PR.

## 6. Design rules — do not bend

- `tole-core` stays platform-agnostic: no stdin/stdout, no CLI assumptions.
  Host interaction goes through traits (`Storage`, `Provider`, `Tool`,
  `Approver`).
- Session storage is append-only JSONL. Never mutate or delete entries;
  corrections are new entries.
- Every non-ReadOnly tool goes through an `Approver`. No bypass path.
  `Destructive` is structurally unregistrable without an interactive
  approver and never allowlistable — do not weaken the three enforcement
  layers (registry / `AllowlistApprover` / host prompt).
- MCP tools are always `Risk::Write`. Server-supplied metadata is never
  trusted for risk classification.
- One capability, every face: a new capability goes into the shared assembly
  (`session::assemble`, `tool_roster`, `turn_runner`), not into one face's
  code. Ask in review: "does this exist on one face only?" If it must, it is
  a row in [docs/faces.md](docs/faces.md) with its reason, and
  `cargo test -p tole-cli --test face_parity` passes (it fails on a
  difference with no row).
- Adding code is a last resort — first check whether configuration or an
  existing mechanism solves the problem.
- Desktop crates are modular monoliths (owner rule D1; the crate cap is 50,000
  lines, the file cap 500): one small module per page or capability, shared
  pieces (text cleaning, badges, caps, strings, tokens) in their own reusable
  modules and not copied, a module directory with small files instead of one
  growing file, a new page as a new module with its own tests. A crate that
  grows toward the cap is split along those module lines first.

## 7. Docs sync

The README status line and `docs/epics.md` must be updated **in the same PR**
that makes them stale. This regression has happened twice (#33 and again
2026-09) — do not ship a third one.

  (`codecoradev/cora-review-action@v1`, `cora-version: latest`) therefore
  runs it: it chunks a large diff (`review.max_chunk_chars`, default 48,000

  install.sh` from the cora-code repository (the `/releases/latest` lookup
  gets a 403 through the container proxy, so pin the version; checksum-only
  without cosign). Without an LLM key `cora review --staged --no-llm` runs the
  deterministic checks only; the agent-as-reviewer path is `cora mcp`.
- **2026-09-18:** cora 0.13.0 no longer reads the legacy `~/.cora/auth.toml`
  / `~/.cora/config.yaml`. Until re-provisioned with `cora auth login`,
  exports are required: `CORA_API_KEY`, `CORA_BASE_URL`, `CORA_MODEL`
  (superseded by the 2026-10-05 note above).
