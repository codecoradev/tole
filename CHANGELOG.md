## [Unreleased]

### BREAKING
- `verify` and `turnend` are sandboxed BY DEFAULT, as `optional` (#748, owner decision of 2026-11-16; ships with the next minor release). When `[sandbox.consumers]` does not set `verify` or `turnend` (an absent key, including a user config written before this change, with no file migrated; `--no-config` gets it too), the mission `--verify` command and the `on_turnend` stop gates run in the `command` sandbox (the workspace writable, `.git` and `.tole` read-only, no `$HOME`, no network, rlimits) wherever bubblewrap works; before, they ran unsandboxed. `run_command`, `job_start` and `cron` stay off by default.
  - **What can break.** A sandboxed command has no `$HOME`, so a `--verify` or gate that needs the toolchain under `~/.cargo` or `~/.rustup` (`cargo test`, `rustc`) exits 127 on EVERY run (a mission ends `verify_failed` after three strikes, a gate is denied three times); one that needs the network or writes outside the workspace fails too; and a git write inside it (`git add`, `git commit`) fails because `.git` is read-only. A workspace layout the `command` profile refuses is now a `verify_refused` mission or a denied gate for default users too, where it used to run: a symlinked `.git`, a sessions directory inside the workspace but not directly under it, a linked worktree or uninitialized submodule inside the workspace, or a working directory that is or holds `$HOME` while `--workspace` points elsewhere (the sandbox binds the process's working directory, not `--workspace`). `tole doctor` warns by name when `~/.cargo/bin` or `~/.rustup` exists.
  - **Why `optional` and not `required`.** `required` would make a sandboxed `cargo` verify fail on every such project and a host without a sandbox refuse every verify; it is not the default and a later release may move there, which is the owner's call.
  - **No sandbox on this host (Windows, macOS, Linux without bubblewrap or user namespaces).** The default degrades instead of refusing: the command runs unsandboxed with `tole: WARNING: verify runs UNSANDBOXED: no sandbox is available on this host (...)` on stderr, a `sandbox_fallback` line (`kind` `sandbox`, `consumer`, `default: true`, `reason`) in the plugin ledger next to the user config, and a WARNING in `tole doctor`. This is the one exception to "no unsandboxed fallback for verify, turnend and cron", and only for the implicit default: a WRITTEN `optional` or `required` still refuses without a sandbox, and so does the default when a backend exists but cannot sandbox the run (a workspace layout the profile refuses, a failing launcher, a program not on `PATH`): `verify_refused`, or a denied gate.
  - **Opt out, per consumer, in the user config:** `[sandbox.consumers]` with `verify = "off"` and/or `turnend = "off"`. `required` (no fallback anywhere) is the strict choice.
  - How the backend is found (stricter for everyone, explicit modes included): `bwrap` must be an executable regular file in an ABSOLUTE `PATH` entry (a relative or empty entry, which means the working directory, is skipped), the first candidate that works is used (a broken earlier one does not decide), the probe runs at start-up whenever `verify` or `turnend` is only the default (before the model runs a command), a definite answer is cached for the process and a transient spawn failure (no process slot, no memory, a signal) is retried and not cached. Where this is stricter an explicit `optional` or `required` refuses where it already would.
  - Embedders: `tole_core::sandbox::command::Consumers` has two new public fields (`verify_implicit`, `turnend_implicit`), so a `Consumers { .. }` literal without `..Consumers::default()` no longer compiles; `Consumers::default()` is still all-off, the `tole` binary uses `Consumers::host_default()`, and an embedder that never calls `set_consumers` sandboxes nothing.
  - `tole config check` prints `sandbox.consumers.verify: not set, so optional (default) ...` for an unset key, so it is not read as off.
  - Related: the `git` tool's hardening (hooks off, config vet) still follows a consumer you WROTE, not this default, and an unresolvable sessions directory is a warning, not a refusal to start, for a default consumer. `tole doctor` shows `verify optional (default)` for the default and `optional` for a written value. Design and the three-state rule: `docs/sandbox-design.md` §9.4 ("The default flip").

### Added
- `tole serve`: a prompt that stops for an approval answers `200 {"stopReason": "approval_required", "approval": {"id", "tool", "status": "pending", ...}}` instead of `refusal` (#571, G0a of the gateway epic #910). The `approval` row has the `GET /approvals` shape. The route snapshots the approval queue before the turn and names only an entry of THIS session and tool queued strictly after that snapshot, so another session's approval is never returned, an older undecided entry is never mistaken for this stop, and the `id` is the one `POST /approvals/{id}/decision` accepts; if that entry expired or was decided before the lookup the answer is still `approval_required` without `approval` (fall back to `GET /approvals?session=<id>`). A stop that queued nothing is a `refusal`: a pre-tool hook denial, a blocked stop gate, an unknown tool, a provider failure and a loop. A turn resumed after an `allow` decision has no HTTP response, so a further approval stop there is only visible through `approval_requested` frames or `GET /approvals?session=<id>` (see `docs/mobile-control.md`). **Compatibility:** `stopReason` gains a value on the serve prompt route only; a client that matched `refusal` exactly to detect an approval stop must match `approval_required` (none known: uteke-mobile polls `GET /approvals`). ACP's `stopReason` values and the MCP `tole_session_prompt` `stop_reason` are unchanged. Embedders (`tole-cli` public API): new `tole_cli::session_host::run_session_turn_detailed` and `#[non_exhaustive] TurnResult`; new `ApprovalQueue::mark`, `ApprovalQueue::queued_since` and `approvals::approval_required_body`; `PendingApproval` gains a `seq` field, so an external struct literal must add it.
- Secrets tole never knew are now masked (#597, owner decision of 2026-11-11). `SecretSet::redact` and `redact_value` run the shared `uteke-privacy` 0.24.1 shape detector (the ruleset uteke uses on its write path) AFTER the known-value pass, at every sink the set already covers (provider request, session log, live events, MCP arguments, web queries, memory loop, and the rest): AWS, GitHub, npm, Slack and Google keys, `sk-` keys, bearer headers, JWTs, PEM private keys, URL passwords and `NAME=value` secrets become `prefix[REDACTED:<kind>]`. It runs for an empty set too, leaves a known value's `«NAME»` marker alone (a second pass can only mask more, never less). A `web_fetch` URL carrying such a shape is refused. False positives: the user-config list `redaction_allowlist` (regexes, user layer only). A JSON object field is masked by its name too (`{"api_key": "<random>"}`), a log entry lists `shape:<kind>` in `redacted`, and a `web_fetch` URL that looks like a secret is refused with its own wording. A `«NAME»` marker is kept only where it is the whole secret position (`user:«NAME»@`, `--password=«NAME»`, `-u user:«NAME»`, an assignment value), never when glued to other text. Caveat: false positives exist (`token = "abc123def456ghi789jkl"`, `https://{user}:{pass}@host`), so an `edit_file` `old_string` copied from masked output will not match; keep them with `redaction_allowlist`. A project config's `redaction_allowlist` is ignored with a warning. Migration: docs/migrating-0.11.md. New dependency: `uteke-privacy` (Apache-2.0, depends on `regex` only). Embedders: `SecretSet::redact` on an empty set is no longer a no-op; `tole_core::secrets::shape::{set_allowlist, check_allowlist, redact_shapes}` are new.
- `tole serve --auth basic`: HTTP Basic auth, first slice of #742 (owner decisions of 2026-11-17: Basic first, one user with many devices, no session bound to an identity, TLS stays at a reverse proxy, the static token unchanged). `--basic-user` (or `TOLE_SERVE_BASIC_USER`) plus the password HASH from `--basic-hash-file` (or `TOLE_SERVE_BASIC_HASH`; there is no hash flag and never a plaintext password) make the credentials; the new `tole serve-hash` reads a password from stdin (a terminal is asked twice, without echo) and prints a salted `$pbkdf2-sha256$i=600000$...` hash (`--iterations`, at least 10000; a stored hash below that is refused). One `Authenticator` now decides every serve route for the bearer token and Basic alike, in the REST face (event stream and uploads included) and in `--transport mcp`; webhooks keep their signature gate. With Basic on, a bearer token that is set keeps working (optional there); `--auth token` is the default and behaves as before (token required, a `401` without `WWW-Authenticate`). A wrong user, a wrong password and a malformed header get one identical `401` with `WWW-Authenticate: Basic realm="tole", charset="UTF-8"` (the hash is always computed, compared in constant time, a credential over 512 bytes is not hashed); failures count in the existing per-IP limiter (`429` after 10 a minute); a verified header is cached for 5 minutes by its SHA-256; the hash is a secret held by role and no error, log line or argument carries a credential. `--auth basic` with a non-loopback `--bind` is refused unless `--allow-insecure-basic` (TLS terminates at a reverse proxy; Basic over plain HTTP is for loopback or a trusted network). Dependencies: `ring` and `base64` are now direct dependencies of `tole-cli`; both were already in the lockfile at these versions (no new package). Not built: OIDC (a later issue), the read-only / full scopes (every credential is full authority), a `[serve.auth]` config table (flags and environment only), more than one user. See `docs/mobile-control.md` and the threat model.
- `tole sessions` shows the serve profile a session recorded (#740): a `profile` column, only when some listed session has one (a malformed recorded name shows as `?`, never as written; without any profile the output is unchanged). `tole doctor` adds `serve profiles: name (room <room>, <n> allow), ...` from the user config: names, rooms and counts only, nothing printed when no profile is defined. This completes #740.
- `tole serve`: a per-session `profile` on `POST /sessions`, create and resume (#740, owner decisions of 2026-11-16). The request names a `[profiles.<name>]` table of the user config (never a project config; an unknown or malformed name is a `400`) and the session uses its persona, model, allow list and memory room. The choice is fixed while the session lives, is recorded in the session log as a `fact/profile` register, wins over the recorded one on resume (`409` when a live session or a removed recorded profile conflicts), and `GET /sessions` shows it. The allow list follows the CLI precedence: an `--allow` flag pins the daemon's list and the profile cannot widen it. A request that sets `memory_room` is refused. Without `profile` nothing changes. See `docs/mobile-control.md`.
- Plugins, #600 slice 3b, `tole plugin audit [NAME] [--json]`: a read-only report per MCP server (tier, state, approved against live manifest hash, binary integrity, secret grants, sandbox profile approved and live, scanner findings of the live tool list or of the stored snapshot, the last three `sandbox_fallback` ledger events) and per skill (status including `approved, unrecorded in the ledger`, hash on disk against the approved one, stated source, last ledger lines). It starts only what `list` would start, never under an agent session, and prints only what `plugin diff` already shows plus scanner findings; every field is redacted, terminal-safe and one line. Writes nothing.
- Plugins, #600 slice 3a, the skills pin: third-party skills are pinned by approved hash with a stated source, in an append-only ledger. `tole skills approve` takes `--source-url`, `--registry-id` and `--pinned-sha` (40 or 64 lowercase hex), recorded as data and never fetched or verified. Each skill approve, revoke and draft promotion is now a line of the new append-only `skill-ledger.jsonl` (written before the approvals file); a skill whose last ledger line is a revoke, or whose approved hash is not the ledger's, stays refused even when `skill-approvals.json` was put back by hand. Residual, stated plainly: an approval the ledger never names (made before the ledger, or after `skill-ledger.jsonl` was deleted) still loads and is reported once at startup as unrecorded, and deleting the ledger makes every approval unrecorded, so it forgets every revoke. An unreadable or over-16-MiB ledger fails startup with the remedy; a ledger torn mid-line by a crash is repaired by the next append. **API note:** the public `tole_core::skill_approval::Approval` gains a `source` field (external struct literals must add it; `Approvals::approve` is unchanged). `tole skills revoke` and `tole skills drafts revoke` are now owner-only. Not built: fetching skills from the uteke registry (no verifiable registry API here), and MCP Registry namespace verification (skipped by the owner). `tole plugin audit` follows as slice 3b.
- Sandbox operability, the logging slice of #750 (design `docs/sandbox-design.md` §11). The start-up line of a sandboxed MCP server now names the profile it runs in (its own binding, not always the default) and the first 12 hex digits of the profile hash, and is one line whatever the names hold. An `optional` MCP server that starts unsandboxed (a human attached, no working bubblewrap or a wrapper that cannot be built) is recorded as a `sandbox_fallback` line in the plugin ledger (server, profile name and hash, reason, time; appended once per server and session, never changing an earlier line; none for `required`, a skipped or remote server, or an unattended run, which refuses). `TOLE_VERBOSE=1` prints the command line of each sandboxed launch (MCP servers and command consumers) to stderr, redacted by the secret set and by secret-shaped flag and `NAME=VALUE` names, never into the session log. `tole doctor` marks `.config/gh`, `.config/glab-cli`, `.config/op`, `.password-store`, `.npmrc`, `.pypirc` and `.cargo/credentials*` as `SENSITIVE` too.
- Opt-in sandbox for cron script jobs and `command:` deliveries, third slice of #748 (design `docs/sandbox-design.md` §9.5). `[sandbox.consumers] cron` = `off` (default, nothing changes) | `optional` | `required`, in the user config only, with the same `command` profile, network and limits as every other consumer; `tole config check` and `tole doctor` show it. A script job or a delivery runs as `bwrap ... -- argv` with the job's `workdir` as the workspace (writable, the top-level `.git`, `.tole`, `.tole-worktrees` and `.gitmodules` paths read-only, data dir and `$HOME` absent, no network unless `host`, rlimits); stdout capture, exit codes, the delivery stdin and `TOLE_CRON_*` variables, the timeouts and the `[secrets]` scrub for `cron` are unchanged. A cron job is unattended, so `optional` counts as `required` and there is no unsandboxed fallback: no backend, a workdir or layout the profile refuses and a launcher that fails or cannot be spawned refuse the job, which settles `error` with `usage.sandbox_refused` and the reason in `usage.error` and the run log (never `ok`), or records the delivery `failed`; nothing extra is printed to stderr per tick. One launcher (`cron/launch.rs`) builds every process `cron` starts. Cron agent jobs still follow `run_command` and `job_start`. A job whose workdir holds the cron dir (`TOLE_CRON_DIR`), or is inside it, is refused too, since a writable bind of either would let the script edit its own ledger and run log. With the cron sandbox on, a path-qualified program (`./job.sh`) is refused as it always was at save time, so a script runs as `sh job.sh`. Public API change for crates.io embedders (a further break is avoided, no `#[non_exhaustive]`): `tole-core` `Consumer` has a new `Cron` variant (`ALL` has five entries), `Consumers` a new `cron` field and `sandbox::command::command_in_dir` is new; `tole-cli`'s `ScriptOutput` gains `sandboxed` and `refused`, and `cron::tick::run_script` and `cron::deliver::RunInfo` take the cron dir. Fixed in the same change: the once-per-process fallback warning had one slot per consumer for four consumers.
- Opt-in sandbox for the mission `--verify` command, second slice of #748 (design `docs/sandbox-design.md` §9.4; the `on_turnend` stop gates are the next entry). `[sandbox.consumers] verify` = `off` (default, nothing changes: the spawned command is the old one) | `optional` | `required`, in the user config only, with the same `command` profile, network and limits as `run_command`. The `sh -c` of `tole mission --verify` runs as `bwrap ... -- sh -c <string>`: the workspace (the process's working directory, as before) writable, the top-level `.git` directory and `.tole` read-only (the #849 protection of the `command` profile, nested gitdirs included), the data dir and `$HOME` absent, no network unless `host`, rlimits, no inherited descriptor above 2; exit status, output capture, the `--verify-timeout` and the `[secrets]` scrub for `verify` are unchanged. A mission is an unattended run, so an `optional` verify counts as `required`; with no working sandbox, or in a workspace layout the profile refuses (an uninitialized or nested submodule, a linked worktree inside the workspace, a `.git` link chain it cannot protect: the refusal says which, and an `optional` verify does not fall back, since a mission is unattended), the verify is REFUSED, never a pass: a check before the first turn ends the mission with status `verify_refused` and a non-zero exit before any model turn is spent (`verify_failures` stays 0; the session stays resumable). A sandbox that passed the check but fails to start the command (a spawn error of `bwrap`, or a non-zero exit for which `bwrap --json-status-fd` reported no exit code of the command) is refused the same way and not blamed on the model. A sandboxed verify can fail every time for environmental reasons that three strikes will not fix: a toolchain under `~/.cargo` or `~/.rustup` is invisible (exit 127), the network is `none` unless `host`, and `memory_mb` limits address space; `tole doctor` says so when `verify` is on and warns when those toolchain directories exist. `tole doctor` lists the consumer (an error for a `required` one, or an `optional` one, with no sandbox) and now says the stop gates, cron scripts and deliveries are not sandboxed yet; `tole config check` shows the key. It stays off by default; making `verify` (and `turnend`) sandboxed by default is a later phase (plan in the design note). A sandbox never replaces an approval. CI's `Sandbox (bubblewrap)` job runs the new tests.
- Opt-in sandbox for the `on_turnend` stop gates, last command consumer of the second slice of #748 (design `docs/sandbox-design.md` §9.4). `[sandbox.consumers] turnend` = `off` (default, nothing changes: the gate is spawned as before) | `optional` | `required`, in the user config only, with the same `command` profile (top-level `.git` and `.tole` read-only, the #849 nested-gitdir protection, data dir and `$HOME` absent, no network unless `host`, rlimits) as `run_command` and verify. Each gate runs as `bwrap ... -- program args` in the workspace; its stdin payload, timeout, output capture and the `[secrets]` scrub for `turnend` are unchanged. A gate may be a program path (`./gate.sh`, `/opt/bin/check`): it must be an executable file and its directory is bound read-only. A stop gate is unattended (nobody answers while the model finishes), so `optional` counts as `required` for it. A refusal is a DENY, never a pass: no working sandbox, a workspace layout the profile refuses (uninitialized or nested submodule, linked worktree inside the workspace), or a launcher that fails to start (a spawn error, or a non-zero exit for which `bwrap --json-status-fd` reported no exit code of the command) denies the turn with the reason and counts toward the 3-denial cap (`stop gate blocked`, exit 6); a gate that ran and failed is an ordinary deny with its own output. A sandboxed gate can fail every time for environmental reasons (a toolchain under `~/.cargo` or `~/.rustup` is invisible, the network is `none` unless `host`): `tole doctor` warns about it. `tole doctor` lists the consumer and now says only cron scripts and deliveries are not sandboxed yet. It stays off by default; making `verify` and `turnend` sandboxed by default is a later phase (plan in the design note). A sandbox never replaces an approval.
- `--sandbox <profile>` and `--no-sandbox` (part of #750). Global flags, owner at a terminal only. `--sandbox <profile>` selects a built-in (`server`, `strict`) or user-config profile for every stdio MCP server in that run (per-server bindings included); it cannot define a profile (a project config's `[sandbox]` is still ignored; it may pick a wider profile the user config defines), cannot turn the sandbox on when `[sandbox] mode` is `off`, and an unknown name is a startup error. `--no-sandbox` starts stdio servers unsandboxed for the run, and is refused when the run is unattended (`tole serve`, `tole acp`, any run without a terminal on stdin and stderr) while the mode is `required` or `optional`. Both flags are refused under an agent session (`TOLE_UNDER_SESSION`, a child agent, #684) and on `tole cron`, `tole hook`, `tole sandbox` and `tole plugin`; the two flags conflict. The flags only change what this run's stdio MCP servers start under (`sandbox::session_policy`); the configured policy (`sandbox::policy`: first-party names, the `plugin add` probe) and the command consumers never see them. As a second layer the core ignores `--no-sandbox` once the process is marked unattended. The startup line and `tole doctor` say that a flag overrode the config. Model-command consumers (`[sandbox.consumers]`) are not affected by either flag.
- Lazy start of locked, sandboxed stdio MCP servers (part of #750), opt-in with `[sandbox] lazy_start = true` in the user config (default off; a project config cannot set it). A server whose lock entry stored a complete snapshot that still hashes to the entry's `manifest_hash` registers its tools from the snapshot and starts on its first call; any other server (no snapshot, a cut, redacted or stale one, `skip`, `--no-sandbox`, HTTP) starts at session start as before. The first call runs the same steps an eager start runs, in the same order: the lock's pre-start decision again (a binary swapped since registration is never started), the normal launch (sandbox plan, startup line logged once, `max_servers`), and the check of the live manifest and version; a refusal stops the server, is ledgered like an eager one, and refuses every later call of the session, so no call reaches an unapproved server. The per-call approval is unchanged. A lazy server offers no resources or prompts. `tole doctor` says when it is on.
- Sandbox profiles per server (#810, part of #750). The user config can define named profiles (`[sandbox.profiles.<name>]`: `workspace`, `network`, `read`, `write`) and bind an MCP server to one (`[sandbox.servers.<name>] profile`), and `[sandbox] profile` can name a defined profile. New `tole sandbox list`, `tole sandbox show <server>` and `tole sandbox set <server> --profile <p>` (user config only; `set` keeps the rest of the file and refuses under an agent session), and `tole config check` prints the effective profile of each server and its source. A project config still cannot set anything under `[sandbox]`, so it can never loosen a profile.

- The sandbox profile in the plugin lock entry (#750, part of it; lock format version 4, an older tole refuses it). An approval records the profile name and a hash of the effective profile (workspace mode, network, the extra read and write paths after symlink resolution) next to the entry, and at every start, before the server is launched and again after it lists its tools, the profile it would run in now must be exactly that one: a profile edited in the user config after approval (a wider network, another grant, a retargeted link), a renamed one, or a sandbox that no longer applies (mode off, a skip entry) blocks the server with the new `Admission::ProfileChanged` until the owner re-approves, at a terminal only (a script's `--hash` is refused for a changed profile; agent sessions cannot approve at all). `tole plugin list` shows the profile and `changed (sandbox profile)`, `plugin diff` prints approved against now. The plugin ledger is the authority: each approval is followed by a `sandbox_profile` line, and a lock whose profile record differs from it (hash edited, record dropped or added) is treated as revoked, so editing the lock cannot loosen a profile; a project lock can pin the profile but never replace or loosen it. Migration: an entry approved before is reported (`list`, `doctor`: approved before approvals recorded their sandbox profile), not blocked, and its profile is compared only after its next `tole plugin approve`. The check reads the profile the server will actually run under, flags included: `--sandbox <p>` with another profile than the approved one, or `--no-sandbox` for a server approved with a sandbox, blocks it for that run, and an approval records the configured profile, never a flag's. Whether the profile moved is decided by the ledger's record, not the lock file alone: a lock hash edited to match a widened profile is itself a move, and a script's `--hash` approval cannot approve past it. A profile applies only where a working sandbox backend exists (`Policy::applied_profile`, shared by approval, admission, `list` and `diff`): a server approved with a sandbox is blocked when bwrap is missing now in mode `optional` (it would run unwrapped), and an approval without a working sandbox records no sandbox. `tole plugin list` and `add` now also name the per-server profile (`[sandbox.servers.<name>]`) in the sandbox status instead of always the default.

### Changed
- The number of participants in a discussion is a recommendation, not a limit (#856). `tole discuss start` and the `discuss` tool no longer refuse more than 8 participants: 8 is `RECOMMENDED_PARTICIPANTS`, and above it the CLI prints `N participants: more than 8 voices mostly add cost and dilute the debate; 3 to 8 is the sweet spot` on stderr (start and `--dry-run`) and the tool result carries the same line in an `advice` array (absent at 8 or fewer). `MAX_PARTICIPANTS` (tole-core) keeps its name but now means the technical ceiling, 16, measured: the most voices whose worst-case round (8000 characters each in 4-byte characters, the scribe's digest refused) fits one 512 KiB ledger record; a contract above it is refused with a message that names it. The cost plan (and `--dry-run`) now shows the floor a round reserves for that many voices and how many rounds the budget covers, and the advice warns before anything is spent when the budget cannot fit one round (still allowed); a round-1 budget escalation now says why. The budget stays a hard cap and nothing else changed: every call is reserved first, `max_rounds`, "every voice must appear", no tools for inline voices, pass-1 sanitizing, user-config profile names only.
- `[discussions] request_timeout_secs` now has a floor of 10 seconds (#813 item 4): 1 to 9 is a startup and `tole config check` error naming the key and the floor, the upper bound (3600) and the default (120) are unchanged. `TOLE_DISCUSSION_TIMEOUT_SECS` may still go down to 1 second, as the documented test hook. A config that set 1 to 9 must raise it to 10 or more.
- `tole doctor` prints a hint when delegation is in use (the user config has a `[delegation]` table, or this workspace's delegation log records a run) and `[delegation] approvals` is unset: without an approver an unattended delegated Write is denied, and `approvals = "owner"` (or `"chain"`) makes the owner the approver (#813 item 1). The default stays `off`; an explicit `off` silences the hint.

### Fixed
- The sandbox backend lookup is stricter and its probe more robust (#748, hardening before the `verify` and `turnend` default flip; found by an independent security review). `bwrap` must be an executable regular file in an ABSOLUTE `PATH` entry: a relative or empty entry (the working directory, which a model can write) is skipped, so a planted `./bwrap` can no longer decide what the sandbox is, and a non-executable `bwrap` earlier on `PATH` no longer shadows the real one; the first candidate that works is used. A probe failure that may pass (a spawn error of kind WouldBlock, Interrupted or OutOfMemory, or bwrap's own EAGAIN, ENOMEM or EINTR message while it creates the namespace) is retried three times and, if it persists, answered but not cached, instead of being cached for the whole process; a clean refusal (user namespaces not permitted) is still a cached negative. For an explicit `optional` or `required` this only makes the sandbox refuse where it already would; it changes nothing else.
- `GET /sessions/{id}/events` no longer sends `ready` after a replay that could not read the session log. A read error on a stream's first replay was retried on the next pass, but `ready` ("the replay is complete") went out anyway, so a client resuming from `Last-Event-ID` or `?after=` could be told it was caught up while it had missed entries. `ready` now waits for a pass that read the log (heartbeats still run meanwhile); streams whose log reads fine behave as before. A plausible cause of the one-off CI failure of `serve_events::a_reconnect_after_a_seq_is_lossless_and_exact` (`left: [] right: [6, 9]`; the flake itself was not reproduced). A failed read is now logged once per stream with its error kind only.

### Security
- `read_file` withholds a file with more than one hard link (#703). A hard link to `.env` under another name (`notes.txt`) matched no name rule and was returned verbatim. On Unix a regular file whose `nlink` is above 1 is now refused, and the refusal points to `read_file_raw` (approval); a single-link file is unaffected, and nothing changes on other platforms. It reads only the `nlink` of the metadata it already has: no directory scan, so a legitimately linked file (a hard-linked build artifact) needs `read_file_raw` too. The git diff filter and `cora_search` hits stay name-based.
- A known secret is now redacted in more of the forms it takes in a sink (#681). The matcher (`SecretSet::redact`) only knew the value alone, its JSON escape, base64 of the value alone and percent-encoding, so `Authorization: Basic base64("user:" + token)`, a docker `config.json` `auth`, a base64'd `.env`, `xxd -p` hex, a JSON `\/` or `\uXXXX` escape (Python `ensure_ascii`, PHP) and a value split by a zero-width character reached the provider, the log and the other sinks unredacted. A value now also matches as base64 (standard and URL-safe) at each of the three offsets inside a larger payload, keeping only the characters that do not depend on the neighbouring bytes, as lower- and uppercase hex, and with `\/` and `\uXXXX` escapes (surrogate pairs included). Text holding a zero-width, bidi or soft-hyphen character is scanned a second time with those characters removed, and the matches are mapped back onto the original. At most 24 needles per value, the 8-character floor still applies (no needle is shorter), and a text without invisible characters is scanned once; redaction throughput on mixed text is about 350 MB/s (was about 660 MB/s). Residual, documented in the threat model: arbitrary transforms (line-wrapped base64, mixed-case hex, gzip, ROT13, a value cut in pieces) are not recognised; the shape detector (#597) cannot close that either.
- A server the plugin lock refuses no longer reaches the model through resources or prompts, and an unapproved or revoked server is not started at all (#680). Before, a refused server's tools stayed out, but tole still connected to it, listed its prompts as `/mcp:` commands, offered it in `mcp_read` (ReadOnly, no approval) and rendered its prompts into the next message. Now `register_server_tools` records the admission decision on the session's own registry (`ToolRegistry::mcp_admitted`, per session, never process-wide), the roster probes extras and offers `mcp_read` only for admitted servers, `tole chat` lists and renders `/mcp:` prompts only for them, and the host skips a server with no lock entry, a revoked one, or every server under an unreadable lock before connecting (`plugin_gate::Gate::refuse_unseen`), with the same refusal note as before. A server whose manifest changed is still connected once, to detect the change. Prompts and resource templates stay outside the manifest hash; they are reachable only from an admitted server.
- Live tool events no longer show secrets the session log hides (#677). The `tool_started` input, the `tool_finished` preview of an output or error, and the reasoning that serve SSE (`GET /sessions/{id}/events`), ACP `tool_call_update` and the TUI forward were the raw values, while the log of the same turn was redacted (#596). The turn loop now redacts every observer event with the session's own secret set (`Storage::egress_secrets`), before the 200-character preview cut, so a cut never leaves part of a secret. Streamed answer text is model output and is not redacted live (its committed entry is).
- The advisor's context no longer lets a secret dodge redaction by being split with an invisible character (#587). `advisor::clean` redacted known secret values and only then stripped control characters, so a value split by a zero-width, bidi or control character (`tok\u{200b}-...`) was not redacted and re-formed once the character was removed. Control and invisible characters (newline and tab kept) are now stripped first, then secrets are redacted, then the fence markers are neutralized, then the text is capped. The multi-round discussion sanitizer (#588) uses the same order.
- A session directory swapped for a symlink no longer redirects the session log (#639). `JsonlStorage` resolves its directory once, walks the canonical path from `/` with `O_NOFOLLOW | O_DIRECTORY` at every component, holds that directory handle, and opens the session file, its `.lock` sidecar and compaction's temp file relative to it (the rename and the directory sync too). Before, `O_NOFOLLOW` covered only the last component, so a job that swapped `.tole` or `.tole/sessions` for a link could have the `.lock` sidecar created elsewhere. Unix only; no new dependency; other targets keep the path-based open. Regression tests swap the directory after `create` and after `open` and assert nothing is created through the link.
- Webhook routes on `tole serve`, part 1b of #582: the security gate. No job is fired yet; filters and the action come in part 2, and `tole hook` in part 3.
  - Each `[hooks.<route>]` table in the user config serves `POST /hooks/<route>`. A project config cannot define or change a route: its `hooks` table is ignored with a warning.
  - A route needs an HMAC-SHA256 key, named by `hmac_key_env` or `hmac_key_file` (a regular file, not a link or FIFO, at most 4 KiB, at least 16 bytes). A route that cannot load stops `tole serve` before it listens, naming the route. Only `insecure_loopback = true` skips the signature, and it loads on a loopback bind only, for loopback clients.
  - Deliveries are checked with `tole_core::webhook` (#643): native `X-Tole-Timestamp` and `X-Tole-Signature` within ±300 s, or GitHub `X-Hub-Signature-256`. The bearer token is not a webhook credential, and a failed signature counts toward the source IP's failed-auth limit.
  - Every delivery id is recorded as `hook_seen` in the cron ledger. A repeat gets `200 duplicate`, after a restart too; an accepted delivery gets `202`.
  - Limits per route:
    - `rate_per_minute` (default 30, at most 600), counted from the ledger so it survives a restart;
    - `max_body_bytes` (default 256 KiB, at most 1 MiB);
    - an unknown route (404) or an oversized body (413) is answered before the body is read.
  - The key never appears in errors, logs, responses, `config check` or the ledger.
  - Accepted limits, written in the threat model:
    - a GitHub delivery replayed after the 7-day retention verifies again, since GitHub signs no timestamp;
    - the ledger grows by one line per accepted delivery and is not rotated;
    - bad-signature limiting is per IP and in memory.

- Sensitive files are read redacted (#598 part b). `read_file` on `.env*`, `*.pem`, `id_*`, `.npmrc`, `.netrc` or `*.key` (file name, case-insensitive, by the requested name or the resolved real path, so a symlink to `.env` counts) returns `KEY=«redacted»` lines, a key file a single `«redacted»`, and no content hash. - Known-value secret redaction, part 1 of #595 (epic #594). - Known-value secret redaction, part 2 of #595: the same `SecretSet` now covers every egress sink tole has today. The provider now redacts tool-call arguments and tool results structurally with `redact_value` (part 1 redacted their serialized text, which turned a secret that is a bare JSON number into invalid JSON; it now becomes the marker string).
- **tole is no longer dumpable on Linux** (#675). Every `tole` process (serve, mission, cron, child agents included) calls `prctl(PR_SET_DUMPABLE, 0)` first thing in `main`. A child running as the same user can no longer read tole's `/proc/<pid>/environ` (which held every secret tole was started with, whatever the ENV-1 scrub removed from the child's own environment) or `/proc/<pid>/mem`, or attach with ptrace. - Multi-round discussion ledger, part 2a of #588: budget hard stops, crash-safe spend and caps. Still no model call and no command.
  - **Every provider call is reserved before it runs** (`reserve`, counted at its estimate) **and settled after it** (`settle`, the estimate replaced by what was spent). A call that does not fit what is left of the budget is not reserved: the budget escalation is recorded at once, wherever the round is, and the discussion goes to its closing step, so a spent budget is a hard stop with an escalation, never a silent end. A call a crash interrupted stays counted at its estimate, so a resumed discussion never spends past its budget; `open_call` and `bind` let a host find a call that runs elsewhere (a delegated child) and poll it instead of starting it again.
  - **A refused digest falls back to the round as written** (`RoundSummary::Fallback`, with a reason of at most 300 characters): only a round big enough for the scribe has one, it holds exactly the round's pass-1 contributions, and it never counts as a round without news.
  - **Caps:** one record at most 512 KiB, one discussion log at most 16 MiB, written as well as read; the last 128 KiB is kept for the gate and the closing record (its text capped at 16,000 characters), so a full log can still be stopped and closed. The log is read with `O_NOFOLLOW | O_NONBLOCK` and a size cap checked on the opened file, and neither the log nor its lock is opened through a symlink.

- Multi-round discussion, the pure core, part 1a of #588 (`tole_core::discussion`, design `profiles-collaboration-secrets.md` A8.3). No model is called and there is no command yet; the ledger (1b) and the orchestration that calls the participants, the scribe and the checker are built on these parts.
  - **Contract**: question, 1 to 12 acceptance criteria (the gate checks them), 1 to 8 participants (profile names), a token budget and max rounds (default 4, at most 10).
  - **Sanitizer pass 1**, deterministic: secrets redacted, control and invisible characters removed, the `<<<` `>>>` fence markers neutralized, sizes capped. Applied to the question, the criteria, every contribution and every digest line.
  - **Digest (pass 2) validator**: a scribe's JSON is read against a fixed schema (decisions, claims, actions, disagreements, open questions, delta). Every line must name a participant of the round and a raw entry of that round written by that same participant; a disagreement needs positions from at least two participants; a participant whose contribution appears nowhere is an error, so dissent cannot be dropped. - Image input on `tole serve` (#558): `POST /sessions/{id}/images` takes one image as the raw request body, sniffs its type from the bytes (PNG, JPEG, GIF, WebP; the request's `Content-Type` is ignored), resolves it through the same core path as `--image` (jail, 10 MiB cap, FNV-1a 64) and stores it content-addressed under `~/.codecora/tole/images/serve/<session id>/`; the answer is `{id, mime, bytes, fnv1a64}` (the id is the hash, no server path). `POST /sessions/{id}/prompt` accepts `"images": [<id>]` next to `text`; only that session's uploads resolve and the turn records the references exactly like `--image` (no blob in the log), so they are re-sent after a restart and `resume`. `GET /sessions/{id}/images/{fnv1a64}` serves only an image recorded in that session's log, re-checking the jail, size and hash of the bytes served, with the recorded `Content-Type` and `X-Content-Type-Options: nosniff`; a mismatch is a `409` (a recorded image outside the jail a `403`), never a silent serve. - Event stream on `tole serve` (#524, third and last part; epic #523): `GET /sessions/{id}/events?after=<seq>` is a Server-Sent Events stream for graphical clients. **Durable** `entry` frames carry the log's entries with their `seq` as the SSE id and replay losslessly after a dropped connection (`after`, or `Last-Event-ID`, which `EventSource` sends itself); `ready` marks the end of the replay. **Ephemeral**, best-effort frames carry streamed text and reasoning, tool start/finish and `approval_requested` / `approval_resolved`; they are never stored or replayed, and a slow client gets a `resync` marker instead of slowing the turn (bounded, non-blocking per-stream queue). A turn only gets live text/tool events when it starts while a stream is open on that session (with no stream open it runs exactly as before); the turn that resumes after an approval streams durable entries only. Heartbeat comment after 15 s without a write (`TOLE_SERVE_HEARTBEAT_SECS`, 1 to 3600, changes it); `closed` and a clean end when the session leaves the live map. At most 8 open streams per server (`429` beyond that), counted within the 32-connection cap so they cannot starve `/approvals` and `/prompt`. Additive: no existing route or response changes. New `events` module (SSE framing, bus, limiter, log tail, approval diff). With this, #524 is complete; the next UI-epic items are #525 and #526. Not included: a stream token for browser `EventSource` (the web client, #529), a log index for very large sessions, an observer for the approvals-resume turn (a `tole-core` change).
- Resume-by-id on `tole serve` (#524, second of three parts; epic #523): `POST /sessions {"resume": "<id>"}` makes an existing session live again, e.g. after a serve restart, so a UI client can reopen it (history via `GET /sessions/{id}/entries`). The id is validated and joined into the session directory only (no client-supplied path); `cwd` goes through the same jail check as a new session and a session is found only under the workspace it was created in (`404` otherwise). An already-live session is returned as is (`alreadyLive`, with its `busy` flag), never reopened, so a running turn is not disturbed. `409` when another process holds the session's writer lock, `503` at the live-session cap with every session busy; a resumed session queues non-preauthorized Writes like a new one. `POST /sessions` for a new session now shares its open-and-admit code with resume, behavior unchanged. - `GET /sessions/{id}/entries?after=<seq>&limit=<n>` on `tole serve` (#524, first of three parts; epic #523): a paginated transcript read for graphical clients. - `evals/shell_usage.py` (#531, step 1): a read-only report over session JSONL of how often `run_command` / `job_start` inputs use shell features (pipe, chain, redirect, substitution, leading `cd`, `bash -c` wrapper), how many failed and how many follow a failed call. - Review gate before `git commit` (#534): while both cora review tools are attached (`mcp_cora_cora_review_prepare` / `_finalize`), a `git commit` is refused until the staged diff has a validated review, and the refusal tells the model exactly how to get one. tole does not hash or record anything itself: it asks cora >= 0.20.0's own commit gate (`cora hook verify`: exit 0 validated or nothing to review, 10 reviewed but blocking, 11 not validated), whose marker is bound to the exact change set, so tole and cora cannot disagree about "this diff". ### Changed
- Storage syncs once per durable commit point instead of once per commit (#483): a tool step issued about 4.8 `fdatasync` calls (5.7 with a Write tool); it now issues 2 (intent before the effect, `finish` after it) and a final answer 1, measured by the new `fsync_budget` test through the real turn loop. New `Commit::defer_sync()` writes a line without syncing; the next durable commit's `fdatasync` persists it. The turn loop defers only the usage row, the `ToolCall` hop, `wrote_this_turn` and the settlement, each always followed by a durable commit. File format, replay, torn-tail repair and poison semantics are unchanged.
- Sequential read-only tool-call batches (#480): when one model response carries several tool calls and ALL of them are registered ReadOnly tools, the turn loop now runs them in model order, each as its own effect sandwich, inside ONE model step, instead of running the first and dropping the rest (the model re-asked each, costing a round trip apiece; measured 11 of 22 calls re-asked on glm-5.1). Any non-ReadOnly or unknown tool in the response keeps the old first-call-only behaviour. This is NOT concurrent execution. A failed call stops the batch and the remaining calls get a `not executed` error result. New additive `Provider::last_extra_tool_calls` (default empty; `ProviderOutput` is unchanged), `machine::begin_batch_member`, and a `"batch": true` marker on the 2nd..Nth intents that the OpenAI wire flattening merges into one assistant `tool_calls` array. Design note: `docs/tool-batches.md`. The PRD non-goal now reads "no concurrent execution; sequential batches supported".
- Release builds use thin LTO, a single codegen unit and `strip = true` (#482): the `tole` binary shrinks from 16.7 MB to about 9 MB. The profile is also set in `crates/tole-cli/Cargo.toml` so `cargo install tole-cli` gets it (the workspace-root profile is not packaged). `panic = "abort"` is deliberately not set: Mutex poison recovery and the serve/ACP/MCP daemons rely on unwinding.

### Fixed
- `--on-pretool`/`--on-posttool`/`--on-turnend` on a build without the `shell-tools` feature (`--no-default-features`) are now refused with a clear error instead of being silently ignored (the hook never ran and a Write tool executed under `--yes`).
- Pre/post hook timeout raised from 5 s to 30 s, matching the turn-end gates (#493): hooks may be verification gates (lint/tests), and a loaded host could exceed 5 s, so the timeout (a non-blocking failure by design) silently skipped the hook and turned a deny into an allow. This was the root cause of the #493 CI flake.
- A denied approval or `--on-pretool` exit 2 no longer strands a headless caller (#476, owner decision 2026-11-03). The turn still parks in Planning, so a bare `tole resume <id>` is unchanged, but `tole resume <id> "<prompt>"` now settles the parked turn and runs the new prompt (it was refused with `run_turn requires pc Idle or Final`), which makes the `--on-pretool` help text true. The denial is now visible to the model's next request through a synthetic user-role `denial_note` entry (marked like the stop-gate feedback, never opens a turn); it was an orphan error entry the wire dropped, so a policy deny was asked for again and again. A denied replay of a crash-interrupted effect now says `the outcome is UNKNOWN: the effect may have run before the interruption; check state before retrying` instead of reading like a user refusal. Denied effects still never execute; the loop guard and step budget are unchanged.
- A non-stream completion with empty content and no tool calls now fails with `malformed response: empty stream (no content, no tool calls)`, like stream mode, instead of returning an empty `Final` with exit code 0 (#478).
- A provider HTTP error now carries its body: `http status: 400 Bad Request — <scrubbed 200-char snippet>`, plus `(retry-after: N)` when the header is present (#474). The chat-completions client no longer lets ureq drop the body of a 4xx/5xx (`http_status_as_error(false)`, that request only); the `/models` probes keep their `Err` on non-2xx. The `http status: N` prefix is unchanged and a snippet never changes retry or failover classification.
- Streaming provider requests reuse one connection (#479): `complete_streaming` stops at `data: [DONE]` and left the chunked terminator unread, so every streamed request opened a new TCP+TLS connection (26 requests, 26 connections; non-stream mode used 1). After a clean end of stream the rest of the body is now read to EOF on a detached `tole-sse-drain` thread, so the turn never waits for it. At most 2 drain threads live per provider (a server that never ends the body parks a thread and socket until the agent timeout); past that, and after an error, the reader is dropped and the connection closes as before. No change to what `complete_streaming` returns.
- A second process can no longer write to a session another process has open (#475): a writable `JsonlStorage` holds an exclusive advisory lock on a sidecar `<id>.jsonl.lock` (survives `compact()`, released by the OS on crash), taken before the torn-tail repair, and `resume`/`chat --resume` against a held session fails with `session is open for writing by pid N` instead of appending stale records (duplicated seq, unreadable session). Each append also checks the file length against the last known good length (new `StorageError::StaleHandle`); `StorageError::Locked` is new. Read-only commands (`status`, `sessions`) are unaffected.
- Approval prompts now also escape the Arabic letter mark (U+061C), the Mongolian vowel separator (U+180E), the word joiner and invisible math operators (U+2060–U+2064) and the deprecated format characters (U+206A–U+206F); they could visually reorder or hide text (pre-tag scan of 0.9.0).
- The API key is redacted from replayed tool-call arguments on the wire, as it already was from message text and tool results (E11).
- Compaction with `keep_turns` of 2 or more no longer cuts before the previous summary, which made the summary call replay the raw transcript and drop that summary. Only embedders could hit it; the CLI keeps one turn.
- `tole sessions`, `sessions --all`, `tole status` and session-name lookup replay session files read-only (`JsonlStorage::open_read_only`): they no longer truncate a torn last line that another process may still be appending.
- `agent_poll` and the concurrent-agent cap no longer treat a recycled pid as the agent: a live pid whose command line does not name the agent (every child is launched with `--sessions-dir <agents>/<id>/sessions`) is another process, so a dead child whose number was reused no longer holds a cap slot or reads as "running" forever (pre-tag scan of 0.9.0). Identity, not clocks or executable names: a wall-clock age check would read a live agent as dead after a clock jump, and a launcher changes the process name. An unreadable command line keeps the plain liveness check.

  defense (hallucinated names get pre-registered with malware; 43% of
  hallucinated names recur, 13% are one character from a real package).
  Not-found answers include registry candidates; one-character
  candidates surface a typo-squat warning; 429/5xx honestly report
  `rate_limited` (never "not found"). The default system prompt tells
  the model to verify before installing.
- Turn-end stop gates (#145, `--on-turnend`, default OFF): deterministic
  script gates that fire when the model produces its final message,
  BEFORE it commits. Deny (exit 2) forces continuation — the reason
  becomes the model's next input and the loop re-runs (the Claude Code
  "stop hook / gate forces the model to fix it" pattern). Bounded: 3
  denials per turn then the turn settles durably as `StopGateBlocked`
  (prompt-resumable). GATE semantics: exit 0 = pass, ANY non-zero exit
  = deny with stdout as the reason (a verification gate's exit code is
  its verdict — cargo check exits 101, tests exit 1); only true
  infrastructure failures (spawn error, timeout) stay non-blocking;
  30s per-hook timeout. Payload carries the final-text preview (8 KiB)
  and the per-turn tool/risk summary.
- Memory-loop decision typing (#143): a session that executed any
  Write/Destructive tool is stored to uteke with `--type decision` and
  a `wrote` tag (plain context sessions unchanged). The flag is durable
  and session-scoped — set on fresh execution AND crash-replay of a
  Write, never reset by turn machinery — and derived from tool risk,
  not model claims. Summary content contract is unchanged: first
  prompt + final answer only.

## [0.4.0] — 2026-10-01

### Added
- Harness memory loop (`--memory uteke` / `TOLE_MEMORY`): on the first
  turn of a fresh session, memories relevant to the prompt are recalled
  from the owner's uteke store (namespace `repo-<dir>`,
  `TOLE_MEMORY_NAMESPACE` to override) and injected into the user
  message inside a clearly marked fenced block — the durable log stores
  exactly what the provider saw. When the session settles with a final
  answer, a compact summary is stored back (`--type context`, tagged
  `tole,session`). Host-initiated on both ends (the model cannot
  trigger or suppress it); every failure degrades to stderr and the
  turn proceeds without memory.
- cora auto-preset: when the `cora` binary is on PATH, tole attaches the
  local `cora mcp` server automatically — the full code-intel surface
  (brain search, callers, impact, affected tests, dead-code, review;
  registry names `mcp_cora_*`). Opt out per run with `--no-auto-mcp`;
  an explicit `--mcp-server cora=...` replaces the preset for that name.
  MCP tools keep the never-trusted trust model: `Risk::Write`, approval
  gate always applies.
- The `tole-cli` default feature set now includes the `mcp` client
  (`default = ["shell-tools", "mcp"]`): the auto-preset and
  `--mcp-server` work on a plain `cargo build -p tole-cli`. Embedder
  profiles are unaffected — `tole-core` defaults do not change.

### Added
- `tole serve --transport mcp` — **multi-session MCP over Streamable
  HTTP** (issue #137): one authenticated MCP connection addresses N
  durable tole sessions. Session tools (`tole_session_new`,
  `tole_session_prompt`, `tole_session_status`, `tole_session_list`)
  ride alongside the registry tools; a `session_id` argument routes a
  tool call to THAT session's registry (workspace jail + approver), and
  an ambiguous no-id call with 2+ open sessions is refused. Served with
  hyper directly (no axum) behind the same bearer-token auth as REST;
  Destructive stays structurally absent (non-interactive approvers).
- `tole serve`: tole as a **token-authenticated HTTP daemon** (issue
  #96, v1) — REST endpoints for the session host: create/list sessions,
  run turns, poll status. Turn execution is serialized per session
  (concurrent prompts get 409), the session map + durable JSONL live
  server-side, and the allowlist approver keeps Destructive tools
  structurally absent (a server has no human to ask). Zero new
  dependencies (hand-rolled HTTP/1.1). Per-connection read/write
  timeouts (30s). MCP-over-HTTP is the follow-up.
- `tole acp`: tole as an **Agent Client Protocol agent** over stdio
  (issue #95) — editors (Zed et al.) drive durable tole sessions:
  `session/new`/`session/load` map to the JSONL session store, prompts run
  full tole turns, the final answer streams as an `agent_message_chunk`,
  and Write/Destructive tool calls surface as
  `session/request_permission` requests — the editor human approves, with
  Destructive consent being a genuine per-call decision. Provider config
  is only required when a prompt actually runs. The session map survives
  across prompts (a first-run regression where fresh state replaced the
  map after one turn — caught by CodeCora review — is fixed, along with
  session-id path-traversal and mutex-poisoning hardening). The
  session-map lock is held only briefly — a running turn keeps its OWN
  storage lock, so the reader loop stays live for permission routing
  (the first implementation deadlocked protocol routing for up to the

  permission request was pending — caught by CodeCora review). Sessions

  registry's hardened tools (jailed file ops, argv-validated git, detached

  client. ReadOnly tools always callable; Write tools pre-authorized via

  listed, read_file round-trip, write without `--allow` denied with an

  instructions; headless multi-mission flows keep one durable session.
  Bare `resume` keeps the approvals-only recovery semantics (#55, #65).

  `OpenAiProvider` response-usage capture; one durable `UsageRecord` per

  wired into a dedicated Evals CI job (wire-shape stability = prefix-

  ledger tokens; Tier 3 per-release baselines with a >25%-regression
  diff gate (`evals/`).

### Changed
- Retry classification: 429/rate-limit responses join timeouts as
  transient and get the one automatic per-turn retry; the durable audit
  entry is now "provider transient failure, retrying" (#58, #62, #66).
- The turn loop no longer clones the full transcript for every provider
  step; `complete()` borrows the storage slice (#66).

### Fixed
- `AllowlistApprover` constructor semantics (#70): documented the
  decision pipeline (pattern match → Allow; `default` applies only to
  NON-matches, so `new(vec!["x"], Decision::Deny)` ALLOWS "x") with a
